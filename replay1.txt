服务范围与目标对象

使用者角色：核心用户是开发、运维、测试，还是包含业务运营人员？不同角色的诉求差异很大。
职责边界划分
重放系统的核心职责是「异常捕获 + 流量重发」，还是包含「根因分析 + 自动修复」？重放成功 / 失败的最终判定权，在重放系统还是由接入方返回的状态决定？

二、异常分类与重放核心规则（业务逻辑核心）
1. 异常准入与分类标准
技术异常：明确纳入范围（如 HTTP 5xx、服务超时、连接失败、限流降级、中间件不可用等），同时明确禁止重放的技术异常（如参数非法 400、鉴权失败 401 等，重放无意义）。
业务异常：明确可重放的业务异常场景（如库存不足、依赖数据未就绪、状态流转冲突），以及绝对禁止重放的敏感场景（如资金扣款、实名核验、已到终态的订单、外部渠道通知等）。
2. 重放触发与执行规则
触发模式：仅支持用户手动触发，还是同时支持「系统自动重试 + 人工手动兜底」？若支持自动重试，需明确重试次数、间隔策略（固定间隔 / 指数退避）、最大重试时长，以及停止自动重试、转为人工处理的条件。
幂等性保障：由重放系统统一生成唯一重放 ID 并透传给下游，还是由接入方自行保证幂等？幂等键的生成规则是什么？
执行顺序：同一业务实体的多条异常记录，是否要求按原始发生顺序串行重放？还是允许并行执行？
内容可改性：是否允许用户修改请求参数、上下文后再重放？还是仅支持原样重放（前者会大幅提升权限和审计要求）。
三、系统可用性检测机制（技术异常的核心能力）
检测对象：技术异常关联的是单个下游系统，还是整条调用链路？当异常涉及多个依赖系统时，是检测全部节点，还是仅检测直接失败的节点？
检测方式与标准
通过什么判定可用性：是调用系统提供的健康检查接口，还是基于近期调用成功率 / 错误率统计，还是对接现有监控系统的告警状态？
判定阈值：连续多少次探活成功、或错误率低于多少，判定为「系统已恢复」？探活频率是多少？
检测后的动作：检测到系统恢复后，是自动触发对应异常的批量重放，还是仅在 UI 上提示「系统已可用」，完全由用户手动触发？
不可用状态的交互：系统不可用期间，是否要置灰 / 屏蔽对应异常的重放入口，避免用户无效操作？
四、批量重放的详细能力
批量维度与规模
支持按哪些条件筛选后批量操作：下游系统、异常类型、时间范围、错误码、业务场景、异常状态等？
单次批量重放的最大条数上限？是否有日 / 小时级的总流量限制？
流量与速率控制
批量重放是否支持配置 QPS / 并发数上限，避免冲垮下游系统？是否支持分时段匀速错峰重放？
不同系统的批量重放是否资源隔离，避免某一系统的大批量操作影响其他系统？
执行与反馈
批量执行策略：并行还是串行？是否支持按时间正序 / 倒序执行？
结果反馈：是否实时展示执行进度、成功 / 失败计数？失败的记录是否支持单独筛选、导出、二次批量重放？
中断机制：批量执行过程中，是否支持人工暂停 / 终止？终止后已执行的记录能否回滚？

数据脱敏：异常请求中的敏感信息（用户隐私、金额、密钥等）在 UI 展示时是否需要脱敏？
六、接入规范、数据与非功能要求
1. 接入与兼容性

容错能力：重放过程中系统宕机，重启后能否断点续跑？是否会重复执行已成功的记录？
业务风险兜底：异常发生到重放的时间窗口内，业务状态可能已变更（如订单已取消），是否需要重放前校验业务状态？由谁校验？
黑名单能力：是否支持配置接口 / 场景级别的重放黑名单，禁止高风险操作？

第八个问题：

下游保障幂等的标准落地规范
统一幂等键规则，平台侧透传
重放平台生成全局唯一的「重放流水号（replay_id）」，每次重放请求强制透传给下游；下游以「业务主键 + replay_id」作为联合幂等键，而非仅用业务单号。
同一条业务记录的多次重放、不同操作可精准区分，避免同订单不同操作被误判为重复请求；原始请求自带唯一 ID 的，可保留原始 request_id 搭配重放次数作为备选方案。
下游幂等实现的硬性标准
数据库层：给幂等键建立唯一索引，从底层兜底防止并发重入。
业务层：严格遵循「查询幂等记录 → 校验业务状态 → 执行业务逻辑 → 写入幂等记录」的同事务流程；交易场景必须叠加状态机校验—— 仅「异常 / 处理中」的中间态允许重放，已成功、已取消、已关闭等终态直接返回原结果，不重复执行业务。
返回约定：统一返回码区分「首次执行成功」「重复执行成功」「执行失败」，便于平台准确统计结果，避免把重复成功判定为异常。
平台侧的配套兜底
单条异常的状态机管控：同一条异常未执行完成时，禁止重复触发重放，兜底避免人为重复提交。
重放流量统一打标：所有重放请求携带特殊标识（如X-Replay-Flag: true），下游可识别后跳过短信通知、外部推送、报表统计等非核心逻辑，规避业务副作用。
交易场景的特殊约束
资金、账务类接口的幂等记录留存周期，必须与业务数据归档周期对齐（通常 3-5 年），禁止提前删除。
批量重放场景下，下游必须保证单条请求独立幂等，不能因批量合并处理破坏单条幂等性。
这套是金融交易系统的通用落地标准，适配你们的场景。

小流量试水重放的判定最佳实践
结合你们当前「重放只管投递、失败靠业务二次上报闭环」的架构，分为 ** 轻量落地方案（适配现状）和进阶成熟方案（交易系统标准实践）** 两类供你参考。
一、适配当前架构的落地方案（零下游改造）
核心逻辑：以「试水消息在约定窗口期内未产生同维度二次异常上报」作为成功判定标准，完全复用现有上报链路。
试水样本配置
优先选取近期新增、覆盖核心交易链路的典型异常，避开已确认是数据问题、必然失败的记录。支持按固定条数（如 5/10/20 条）或积压总量比例（如 1%）配置试水规模，初期建议固定数量更可控。
判定窗口期设置
窗口时长按业务消息处理 SLA 的 2~3 倍配置（例如正常单条消息消费处理耗时 30s，窗口期设 1~2 分钟），需覆盖 Solace 队列投递延迟 + 业务处理全链路耗时。支持按异常类型、下游系统分别配置。
核心判定规则
试水成功：窗口期内，所有试水消息对应的「业务主键 + 异常类型」均未出现新的异常上报，判定通过，可自动触发后续全量批量重放，或通知操作人员确认后执行。
试水失败：窗口期内任意 1 条试水消息产生二次异常上报，立即判定失败，终止批量计划，同时标记该异常类型为 “持续失败” 并触发告警。
兜底机制
若窗口期超时后既无二次上报、也无明确回执，默认按 “试水通过” 处理，但需在操作日志中标记「无明确回执，默认通过」，同时保留人工复核入口，高风险场景需人工确认后再启动批量。
二、交易系统进阶最佳实践
金融交易场景的成熟方案普遍采用「阶梯式放量 + 多维度联合校验」，最大程度降低系统恢复不彻底带来的二次冲击：
阶梯式逐级放量
不做 “一次试水就全量”，分阶梯验证，每一级通过后再进入下一级：
第一级：小流量试水（5~10 条），验证核心链路可用性
第二级：10% 流量试水，验证系统基础吞吐能力
第三级：50% 流量试水，验证全链路稳定性
最终：100% 全量重放
每一级的流量比例、窗口期均可独立配置，适配不同严重程度的故障场景。
多维度联合判定
不单一依赖异常上报，结合多个信号综合判断系统恢复状态：
基础设施信号：健康检查接口连续 N 次返回成功（与你们现有方案对齐）
业务结果信号：试水消息无二次异常上报
队列监控信号：对接 Solace 队列监控，原始队列消费堆积持续下降、无新增积压
失败熔断冷却
单次试水失败后，自动进入冷却周期（如 5 分钟），冷却期内禁止再次自动试水，避免反复投递加重下游负担；冷却结束后可自动重试 1 次，仍失败则转为人工介入。
人工确认兜底
高风险场景（如账务类异常、积压量超千条），即使试水判定成功，也仅生成批量重放预案，通知操作人员人工复核确认后再执行，避免策略误判引发资损风险。

第 46 个问题：
归档动作目前是仅支持系统按配置的保留天数自动定时执行，还是同时支持人工手动选择指定范围（如时间区间、业务线）的数据发起归档；归档操作、归档数据导出是否需要配置独立权限点进行管控？
暂时只支持统一归档设置

已确认第 46 项需求：
归档动作本期仅支持统一配置的系统自动定时执行，按全局设置的在线库保留天数自动完成超期数据归档；暂不支持人工手动选择时间区间、业务线等指定范围发起归档，也暂不支持按业务线差异化配置归档规则。
第 47 个问题：
在综合查询菜单检索异常记录时，是否需要系统自动跨在线库与归档库执行统一查询，用户无需感知底层数据源差异；还是需要用户手动选择查询范围（仅在线数据、仅归档数据）后再发起检索？
分开两个查询

已确认第 47 项需求：
综合查询拆分两个独立查询入口，分别对应在线库异常记录查询、归档库异常记录查询，用户手动选择对应入口发起检索，底层数据源相互隔离，查询范围清晰区分。

已确认第 48 项需求：
在线库与归档库的两套查询入口，筛选维度、列表展示字段保持一致，保证查询体验统一。
